Every agent has one **draft** and a linear history of **published versions**. Edits in the Builder or via the API always land in the draft. Production sessions never see them until you publish. Publishing snapshots the draft into an immutable, numbered version and makes it the **live** version, the one new sessions run. A [rollback](#roll-back-the-live-version) can later make an earlier version live again.

## Draft vs. published

|            | Draft                                                                                   | Published version                             |
| ---------- | --------------------------------------------------------------------------------------- | --------------------------------------------- |
| Mutability | Editable: Builder and `PATCH .../config` write here                                     | Immutable snapshot                            |
| Used by    | [Preview calls](/agents/test/preview-calls) and [agent tests](/agents/test/agent-tests) | Production sessions: web, SDK, and phone      |
| History    | One per agent, always current                                                           | `version_number` increments with each publish |

<Note>
  An agent that has never been published cannot take production sessions:
  session creation returns `409` until the first publish.
</Note>

Phone number settings are not part of the agent, so they are not versioned. Which agent a number is bound to, its [transfer caller ID](/agents/telephony/transfers#caller-id-on-transfers), and an [imported number's SIP configuration](/agents/telephony/byo-sip#update-the-configuration) live on the number. Changes to them apply from the next call without publishing, and publishing or rolling back the agent never changes them.

## Publish the draft

<Tabs className="console-api">
<Tab title="Console" icon="browser">

<Steps>
  <Step title="Edit: changes autosave">
    Every change is written to the draft automatically; the **Saving… / Draft
    saved** indicator in the top bar shows the current state.
  </Step>
  <Step title="Watch the unpublished-changes indicator">
    When the draft differs from the last published version, the **Publish**
    button becomes active with an unpublished-changes hint next to it. When
    there is nothing new to publish, the button is disabled. An agent that has
    never been published always counts as having changes.
  </Step>
  <Step title="Publish">
    Click **Publish**. Any pending edits are saved first, then the draft is
    snapshotted as the next version. A confirmation shows the new version
    number, and the agent shows as **Live** in your agents list.
  </Step>
</Steps>

</Tab>
<Tab title="API" icon="code">

Configuration edits (`PATCH`) go to the draft; a separate `publish` call rolls them out. A `version_title` and `version_description` are optional and make the version history easier to audit:

```bash Update the draft
curl --request PATCH "https://api.fish.audio/v1/agent/agents/$AGENT_ID/config" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "prompt": { "system_prompt": "You are a concise support agent for Acme." }
  }'
```

```bash Publish
curl --request POST "https://api.fish.audio/v1/agent/agents/$AGENT_ID/publish" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{ "version_title": "Tighten support tone" }'
```

The publish response includes the new `version_number`. If the draft is identical to the live version, no version is created and the response has `created: false`. Each publish that creates a version is recorded in the [deployment history](#deployment-history).

</Tab>
</Tabs>

New sessions use the newly published version from that point on. To hear a change before it goes live, run a [preview call](/agents/test/preview-calls). Previews always use the draft.

## Version history

List published versions, or fetch the complete configuration snapshot of any one of them, including the version currently serving production:

```bash List versions
curl "https://api.fish.audio/v1/agent/agents/$AGENT_ID/versions" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

```bash Get one version's snapshot
curl "https://api.fish.audio/v1/agent/agents/$AGENT_ID/versions/3" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

Each version record includes:

| Field                 | Description                                                                                |
| --------------------- | ------------------------------------------------------------------------------------------ |
| `version_number`      | Auto-incrementing, unique per agent                                                        |
| `version_title`       | Optional label sent when publishing                                                        |
| `version_description` | Optional description sent when publishing                                                  |
| `config_hash`         | Fingerprint of the configuration snapshot                                                  |
| `published_at`        | When the version was published                                                             |
| `is_live`             | `true` for the version new sessions run. Exactly one version of an agent is live at a time |

The live version is not always the highest `version_number`: after a [rollback](#roll-back-the-live-version) an older version is live. Check `is_live` to see which version is serving production.

Fetching a single version returns the full configuration as it was published. Because `GET .../config` always shows the draft, the snapshot endpoint is how you read back what is actually running in production.

<Warning>
  Version snapshots never echo credential secrets. Write-only fields (such as
  webhook secrets and tool authorization headers) return a `has_secret: true`
  marker instead of the value, and the custom LLM [`api_key` and
  `headers`](/agents/build/custom-llm) read back as `null`, in every version
  including historical ones.
</Warning>

## Edit a version title and description

The title and description of a published version can be changed at any time, including on the version that is live. Only the labels change: the frozen configuration and its `config_hash` stay as they were.

```bash Change a version's labels
curl --request PATCH "https://api.fish.audio/v1/agent/agents/$AGENT_ID/versions/3" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{ "version_title": "Tighter greeting", "version_description": null }'
```

Each field behaves the same way:

- A string sets the label.
- An explicit `null` clears it.
- An omitted field keeps its current value, so `{}` changes nothing.

The response is the updated version record, without the configuration snapshot.

## Roll back the live version

A rollback switches the live version to any published version, older or newer than the current one. It moves the live pointer and nothing else: no version is created, and your draft keeps its current content, including edits you have not published. New sessions and incoming calls use the target version at once; sessions already in progress keep the version they started on.

```bash Switch the live version to version 1
curl --request POST "https://api.fish.audio/v1/agent/agents/$AGENT_ID/versions/1/rollback" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "expected_live_version": 2,
    "reason": "New booking tool returns 404 until the backend ships"
  }'
```

The request body is optional. Every field in it is optional too:

| Field                   | Description                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `expected_live_version` | Switch only while this is the live version number; see [Switch only if nobody else has](#switch-only-if-nobody-else-has) |
| `reason`                | Why the live version is moving (up to 500 characters). It is kept on the [deployment record](#deployment-history)        |

The response describes the switch:

| Field                     | Description                                                                          |
| ------------------------- | ------------------------------------------------------------------------------------ |
| `version`                 | The version that is live now, with `is_live: true`. It has no configuration snapshot |
| `previous_version_number` | The version that was live before the call                                            |
| `changed`                 | `true` when the live version moved, `false` when the target was already live         |

```json Response
{
  "version": {
    "version_number": 1,
    "version_title": "Initial release",
    "version_description": null,
    "config_hash": "sha256:4e7a1c9d…",
    "published_at": "2026-11-10T08:15:42.120000Z",
    "is_live": true
  },
  "previous_version_number": 2,
  "changed": true
}
```

To read the configuration that is now running, fetch it with `GET .../versions/{version_number}`.

When the target is already the live version, the call changes nothing and returns `changed: false`. No deployment record is written either.

The draft is not touched, so it can differ from the version that is now live. Compare the `config_hash` from [Get Draft Config](/api-reference/endpoint/agent/get-draft-config) with the live version's to see whether it does. If the draft still carries the change that caused the problem, fix it before you publish again.

### Switch only if nobody else has

Read the live version from the version list and pass its number as `expected_live_version`. If someone has published or rolled back in the meantime, the call fails with `409` and `reason: "live_changed"`, returns the version that is live now, and writes nothing.

```json 409 live_changed
{
  "status": 409,
  "reason": "live_changed",
  "message": "Live version does not match expected_live_version; read the versions again before rolling back",
  "live_version_number": 3
}
```

### When the target version needs something that is gone

A version is a frozen snapshot, so a rollback runs it exactly as it was published. If that snapshot points at a resource that no longer exists, the call fails with `409` and `reason: "missing_references"`, and the live version stays as it is. `missing` lists what could not be found:

| `type`                      | What is missing                                             |
| --------------------------- | ----------------------------------------------------------- |
| `integration_connection`    | An integration connection that was deleted                  |
| `knowledge_source`          | A knowledge source that was deleted or archived             |
| `knowledge_source_revision` | The pinned revision of a knowledge source that still exists |

```json 409 missing_references
{
  "status": 409,
  "reason": "missing_references",
  "message": "The version references resources that are no longer available; restore or detach them first",
  "missing": [{ "type": "integration_connection", "id": "<connection id>" }]
}
```

Restore the resource, or choose another version.

Rolling back from the console's version history works the same way: it moves the live version without creating a version or changing the draft.

### Publishing after a rollback

[Publishing](#publish-the-draft) always starts from the draft. After a rollback the draft usually differs from the live version, so the next publish creates a new version with the next number and makes it live. Edit the draft first if it still contains the change you rolled back from. If the draft happens to match the live version, nothing is created and the response has `created: false`.

### Example: switch back, then forward again

Version 2 added a booking tool, but your backend is not ready for it and the tool returns `404` on live calls. Version 1 is fine.

<Steps>
  <Step title="Find the live version">
    List the versions and look for `is_live`. Here it is version 2.
  </Step>
  <Step title="Switch back to version 1">
    Call the rollback endpoint with `expected_live_version: 2` and a `reason`
    as above. The response has `changed: true`. New calls use version 1. Your
    draft still has the booking tool, so you can keep working on it.
  </Step>
  <Step title="Fix the problem">
    Fix the backend, or change the configuration in the draft and test it with
    a [preview call](/agents/test/preview-calls).
  </Step>
  <Step title="Go forward again">
    If the fix was in the backend, switch to version 2 with the same call,
    now against version 2. No new version is created.

    ```bash Switch the live version back to version 2
    curl --request POST "https://api.fish.audio/v1/agent/agents/$AGENT_ID/versions/2/rollback" \
      --header "Authorization: Bearer $FISH_API_KEY" \
      --header "Content-Type: application/json" \
      --data '{
        "expected_live_version": 1,
        "reason": "Backend is fixed"
      }'
    ```

    If you fixed it by changing the configuration instead,
    [publish](#publish-the-draft) the draft: that creates version 3 and makes
    it live.

  </Step>
</Steps>

To bring back only part of an old version into the draft, read its snapshot with `GET .../versions/{version_number}` and `PATCH` just those sections into the draft config. That updates the draft without publishing: [preview](/agents/test/preview-calls) it, then publish. Because snapshots never echo secrets, credential fields keep their current draft values unless you set them again.

## Deployment history

Every change of the live version is recorded: each publish that creates a version, and each rollback that moves the live version. A publish that finds nothing new and a rollback to the version that is already live are not recorded. Read the history to see what was live when, and who or what moved it:

```bash List deployments
curl "https://api.fish.audio/v1/agent/agents/$AGENT_ID/deployments?page_size=10" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

```json Response
{
  "deployments": [
    {
      "deployment_id": "5b0c9e2f7a1d4e8b9c3f6a0d2e7b4c19",
      "action": "rollback",
      "version_number": 1,
      "previous_version_number": 2,
      "source": "api",
      "reason": "New booking tool returns 404 until the backend ships",
      "created_at": "2026-11-23T08:12:40.118000Z"
    },
    {
      "deployment_id": "a3d71e0c5b2f4986b1e7c4d90f6a2b53",
      "action": "publish",
      "version_number": 2,
      "previous_version_number": 1,
      "source": "console",
      "reason": null,
      "created_at": "2026-11-22T14:03:11.402000Z"
    }
  ],
  "has_more": true,
  "next_cursor": "<cursor>",
  "total": null
}
```

The newest change comes first. Each record has:

| Field                     | Description                                                                                                                        |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `deployment_id`           | Identifier of this record                                                                                                          |
| `action`                  | `publish` when a published draft became a new version and went live, `rollback` when the live version moved to an existing version |
| `version_number`          | The version that went live                                                                                                         |
| `previous_version_number` | The version that was live before, or `null` for the agent's first publish                                                          |
| `source`                  | Where the change was made: `console`, `api`, or `unknown` for changes from before deployments were recorded                        |
| `reason`                  | The `reason` sent with a rollback, or `null`                                                                                       |
| `created_at`              | When the live version changed                                                                                                      |

Page through the list with `page_size` (1 to 100, default 30) and either `cursor` (the `next_cursor` of the previous page) or `page` (starting at 1). The two are mutually exclusive and sending both returns `400`. The response also has `has_more`; `total` is included in `page` mode, or when you send `include_total=true`.

## Clone an agent

Cloning creates a new agent from an existing one's **draft** configuration. In the console, open the agents list and choose **Clone** from the agent's row menu. Over the API, send a `POST` with no body:

```bash Clone an agent
curl --request POST "https://api.fish.audio/v1/agent/agents/$AGENT_ID/clone" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

The response is the new agent, with status `201`. It is named `<name> copy` (truncated to 120 characters) and keeps the source's description. Rename it with [Update Agent](/api-reference/endpoint/agent/update-agent).

| Copied                                                                                        | Not copied                                                                           |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| The draft configuration, including credentials such as webhook secrets and the custom LLM key | Published versions and deployment history                                            |
| Attached tools and integration connections                                                    | Agent-private knowledge sources                                                      |
| Workspace knowledge sources                                                                   | Phone numbers bound to the source agent                                              |
| The data retention setting                                                                    | Agent tests                                                                          |
|                                                                                               | Public access, allowed origins, and session overrides (they start at their defaults) |

The clone is created in the same workspace as the source, so the workspace-level tools, knowledge sources, and connections it references stay valid. An archived agent cannot be cloned and returns `404`.

The new agent is unpublished: its `publication_state` is `draft`, and it cannot take production sessions until you [publish](#publish-the-draft) it. Use clones to template a base configuration across many agents, or to experiment without risking an agent that is already live.
