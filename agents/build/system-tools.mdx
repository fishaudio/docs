System tools are capabilities built into the platform. There is nothing to create or host. Each agent simply enables the ones it needs.

| Tool | Key | What it does |
|---|---|---|
| Hang up call | `hang_up_call` | Lets the agent end the call itself. |
| Press keys (Beta) | `press_keys` | On outbound calls, lets the agent press phone keys to get through an automated phone menu. |

## Toggle a system tool

<Tabs className="console-api">
<Tab title="Console" icon="browser">

Open your agent's **Tools** page in the Builder. The **System tools** card holds a switch for each tool.

</Tab>
<Tab title="API" icon="code">

Set the switches under `tools.system_tools` in the agent's config. A switch is `true` or `false`, except `press_keys`, which is an object with `enabled`. Switches you leave out keep their current value. The change goes to the draft, so [publish](/agents/deploy/versions-publishing) afterwards.

```bash Request
curl --request PATCH "https://api.fish.audio/v1/agent/agents/$AGENT_ID/config" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "tools": {
      "system_tools": {
        "hang_up_call": true,
        "press_keys": { "enabled": true }
      }
    }
  }'
```

`GET /v1/agent/agents/$AGENT_ID/config` returns every switch in the same place.

```json Response
{
  "tools": {
    "system_tools": {
      "hang_up_call": true,
      "hang_up_call_farewell_mode": "generated",
      "hang_up_call_farewell_message": "",
      "hang_up_call_refuse_questions": true,
      "press_keys": { "enabled": true }
    }
  }
}
```

The response has more fields than shown here. See [Configuration](/agents/build/configuration) for the rest of the config.

</Tab>
</Tabs>

## Hang up call

With **Hang up call** on, the agent can end the call itself by calling the built-in `_end_call` tool. The call ends once the agent finishes speaking.

### Farewell

Choose what callers hear before the call ends.

| Mode | Behavior |
|---|---|
| **Generated** (default) | The agent writes a short goodbye into the tool call's `message`, and the caller hears it. |
| **Fixed message** | The agent ends with the exact text you provide. |
| **Off** | The call ends as soon as the agent finishes its current reply, with no extra goodbye. |

In every mode, anything the agent says in the same reply as the `_end_call` call is spoken first. In **Generated** mode, `message` is said only when that reply says nothing, so callers never hear two goodbyes.

<Tabs className="console-api">
<Tab title="Console" icon="browser">

On the agent's **Tools** page, turn on **Hang up call** in the **System tools** card. Pick a mode under **Farewell** below it. For **Fixed message**, type the line in the box that appears.

</Tab>
<Tab title="API" icon="code">

Set `tools.system_tools.hang_up_call_farewell_mode` to `generated`, `fixed`, or `off`, and put the fixed text in `tools.system_tools.hang_up_call_farewell_message`.

```bash Request
curl --request PATCH "https://api.fish.audio/v1/agent/agents/$AGENT_ID/config" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "tools": {
      "system_tools": {
        "hang_up_call": true,
        "hang_up_call_farewell_mode": "fixed",
        "hang_up_call_farewell_message": "Thanks for calling Acme. Goodbye!"
      }
    }
  }'
```

</Tab>
</Tabs>

The fixed message is up to 1,000 characters and accepts the same `{{placeholders}}` as the system prompt (see [Dynamic variables](/agents/build/dynamic-variables)). A fixed mode with an empty message falls back to **Generated**.

### Questions before hanging up

Turn on **Don't hang up on a question** to stop the agent from hanging up on a question. With it on, if the `message` the caller would hear contains a question mark, for example "Is there anything else I can help you with?", the `_end_call` call fails and the call stays open. The agent asks the question in its reply, waits for the answer, and calls `_end_call` again after that.

<Tabs className="console-api">
<Tab title="Console" icon="browser">

On the agent's **Tools** page, under **Hang up call**, set **Farewell** to **Generated**, then turn on **Don't hang up on a question**. The switch shows only in **Generated** mode.

</Tab>
<Tab title="API" icon="code">

Set `tools.system_tools.hang_up_call_refuse_questions` to `true`.

```bash Request
curl --request PATCH "https://api.fish.audio/v1/agent/agents/$AGENT_ID/config" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{ "tools": { "system_tools": { "hang_up_call_refuse_questions": true } } }'
```

</Tab>
</Tabs>

The switch has no effect with a **Fixed message** or **Off**. Agent tests and simulations follow the same setting.

## Press keys

<Note>
  Press keys is in Beta. The instructions the agent gets for it, and when
  exactly a key goes out, may still be tuned.
</Note>

Many business numbers are answered by an automated phone menu before a person picks up. With **Press keys** on, the agent can get through that menu on the calls it places. On [outbound calls](/agents/telephony/outbound-calls) it gets two more tools.

| Tool | What the agent does with it |
|---|---|
| `_press_keys` | Presses keys on the phone keypad, such as a menu option, an extension or an account number. |
| `_skip_turn` | Stays silent for a turn and keeps listening, while a menu is still reading its options or a hold message plays. |

The agent decides from what it hears. A call to a company's main line can go like this.

<Steps>
  <Step title="A menu answers">
    "For sales, press 1. For support, press 2." The agent presses 2 and says
    nothing.
  </Step>
  <Step title="The call is on hold">
    "Please hold for the next available representative." The agent stays
    silent and keeps listening.
  </Step>
  <Step title="A person answers">
    "Support, this is Amy." The agent talks to Amy as on any other call.
  </Step>
</Steps>

The setting applies to outbound phone calls only. Inbound calls, web and SDK sessions ignore it. To press keys on the call to a transfer destination, see [Pressing keys on a transfer](/agents/telephony/transfers#pressing-keys-on-a-transfer).

### Turn it on

<Tabs className="console-api">
<Tab title="Console" icon="browser">

On the agent's **Tools** page, turn on **Press keys** in the **System tools** card, then [publish](/agents/deploy/versions-publishing). Outbound calls run the published version.

</Tab>
<Tab title="API" icon="code">

Set `tools.system_tools.press_keys.enabled`, then [publish](/agents/deploy/versions-publishing).

```bash
curl --request PATCH "https://api.fish.audio/v1/agent/agents/$AGENT_ID/config" \
  --header "Authorization: Bearer $FISH_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{ "tools": { "system_tools": { "press_keys": { "enabled": true } } } }'
```

</Tab>
</Tabs>

### Tell the agent where to go

The agent picks keys from the menu it hears and from its system prompt. Say in the prompt who it should reach, and give it every number it may be asked for. The agent only enters numbers that are in its instructions or that the phone system itself reads out. Pass values that change per call as [dynamic variables](/agents/build/dynamic-variables).

```text
You are calling {{clinic_name}} to confirm an appointment for {{patient_name}}.
If an automated system answers, choose the option for appointments or the
front desk. If it asks for an extension, enter {{extension}}.
When a person answers, introduce yourself and say why you are calling.
If you reach voicemail, leave a short message with the callback number.
```

### Test key presses

[Agent tests](/agents/test/agent-tests) on the **Phone outbound** channel give the agent the two tools, so you can check what it presses before it places a call. A test sends no tones. It checks the keys the same way a call does and shows each press as a `_press_keys` tool call.

| Test type | What it checks |
|---|---|
| Tool | The phone system's line is the user's message, for example `For sales, press 1. For support, press 2.` The test checks `_press_keys` with the parameter `keys`, here `2`. Spaces and dashes the agent writes into a number are ignored, so `1-800 555` matches `1800555`. A test on `_skip_turn` checks that the agent stays silent through a hold message. |
| Simulation | The scenario describes the phone system, with the menu it reads, where each key leads and who answers in the end. The simulated user is told which keys the agent pressed and answers as that system would. A required tool call on `_press_keys` checks the keys you expect. |

<Tabs className="console-api">
<Tab title="Console" icon="browser">

In the test, set **Channel** to **Phone outbound**. For a Tool test, write the menu line as the **User** message, pick `_press_keys` under **Require tool execution** and add the parameter `keys` under **Tool parameters**. For a Simulation test, write the phone system into the **Scenario**, then open **Advanced** and add `_press_keys` under **Required tool calls**.

</Tab>
<Tab title="API" icon="code">

A Tool test sets `channel` to `phone_outbound` and references the tool by its name with the type `system`.

```json
{
  "name": "Presses 2 for support",
  "test_type": "tool",
  "agent_ids": ["<agent-id>"],
  "channel": "phone_outbound",
  "conversation": [
    { "role": "user", "text": "For sales, press 1. For support, press 2." }
  ],
  "referenced_tool": { "id": "_press_keys", "type": "system" },
  "tool_parameters": [{ "name": "keys", "value": "2", "type": "string" }]
}
```

A Simulation test sets `simulation.channel` to `phone_outbound` and adds the same tool to `simulation.assertions.tool_calls`, with the keys under `params`. [Agent tests](/agents/test/agent-tests) lists every field.

</Tab>
</Tabs>

A test on any other channel does not include the two tools, as a real call there does not. A Single Turn test on Phone outbound has them as well, so a reply to a menu line can be empty.

### Limitations

- **Imported SIP numbers.** Keys are sent as telephone events (RFC 4733). On an [imported SIP number](/agents/telephony/byo-sip) they reach the other side only when your SIP provider carries them. Place a test call to a menu to confirm.
- **Preview calls.** [Preview calls](/agents/test/preview-calls) are web sessions and do not include the two tools.

## Transfer call

`_transfer_call` has no switch of its own: it is enabled automatically once the agent has a transfer destination configured, and only on phone sessions (web sessions have no call to transfer). See [Transfers](/agents/telephony/transfers) for configuring destinations and everything else about transfers.
