Every production session your agents handle (from the API, the console, [public agents](/agents/deploy/public-agents), or [phone calls](/agents/telephony/inbound-calls)) is queryable over REST: a lightweight list for browsing, a merged timeline of messages and tool activity per session, and per-speaker recordings when the agent [records audio](#what-gets-stored). You can query a session while the call is still in progress.

This is a server-side API: authenticate with your API key. The client SDKs deliberately expose no history interface; fetch history from your backend and pass it to your frontend as needed.

## What gets stored

Each production session stores a session record (status, timing, caller attribution, name, `end_user_id`, and `metadata`) and the conversation transcript. Audio recording is a per-agent choice, on by default: set `conversation.record_audio` in the console under your agent's **Settings** or in the `conversation` section of the [config API](/agents/build/configuration#configure-through-the-api), with a per-session override on the [session request](/agents/deploy/authenticated-sessions). Recording off means there is no audio to download.

The setting doesn't affect the live call: transcript events still stream to connected clients in real time.

<Warning>
  Recording defaults to on. Call-recording laws vary by jurisdiction. Make sure
  callers are informed and consent where required before going live.
</Warning>

## List sessions

`GET /v1/agent/sessions` returns session facts, newest first. The list is intentionally thin (no transcripts or tool details) so it stays fast at any volume.

<CodeGroup>
```bash API (curl)
curl "https://api.fish.audio/v1/agent/sessions?agent_id=YOUR_AGENT_ID&status=completed&page_size=50" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

```python Python
import os
import httpx

resp = httpx.get(
    "https://api.fish.audio/v1/agent/sessions",
    params={"agent_id": "YOUR_AGENT_ID", "status": "completed", "page_size": 50},
    headers={"Authorization": f"Bearer {os.environ['FISH_API_KEY']}"},
)
sessions = resp.json()["sessions"]
```

</CodeGroup>

Each row carries the session facts:

```json
{
  "sessions": [
    {
      "session_id": "…",
      "agent_id": "…",
      "agent_name": "Support agent",
      "name": "Order #4821 follow-up",
      "end_user_id": "user_42",
      "status": "completed",
      "end_reason": "user_hangup",
      "conversation_status": "resolved",
      "source": "phone",
      "caller_number": "+15551234567",
      "caller_id_withheld": false,
      "dialed_number": "+14155550100",
      "sip_call_id": "7f3a9c@sbc.example.com",
      "call_sid": "CA5d3a…",
      "started_at": "2026-07-22T09:14:02+00:00",
      "ended_at": "2026-07-22T09:16:05+00:00",
      "duration_seconds": 123,
      "metadata": { "crm_ticket": "T-4821" }
    }
  ],
  "has_more": true,
  "next_cursor": "…"
}
```

`caller_number` and `dialed_number` are set for phone sessions only (E.164) and are `null` for web sessions. `caller_id_withheld` is `true` when the carrier hid the caller's number, and then `caller_number` is `null` too (`anonymous` and Twilio's placeholder numbers count as hidden). It is `false` on phone and WhatsApp sessions whose caller number was shown, on outbound calls, and on calls made before the field existed, and `null` on web and other non-call sessions. `sip_call_id` is the SIP `Call-ID` of the call's INVITE. It is `null` on web sessions and on outbound calls that were never answered. See [Match calls with your SIP records](/agents/telephony/byo-sip#match-calls-with-your-sip-records). `call_sid` is the carrier's id of the call: Twilio's CallSid on an inbound call through a Twilio number, the same value the [inbound call webhook](/agents/monitor/webhooks#inbound-call-webhook) sends. It is `null` on other sessions. `name` is the display name you passed when creating the session (`null` when omitted), `end_user_id` is the end-user identifier you passed (`null` when omitted), and `metadata` echoes back whatever you attached when creating the session. `conversation_status` says how the conversation went (see [Conversation status](#conversation-status)). Whether a session has a recording you can download is answered by the [recording endpoint](#download-recordings).

### Status and end reason

`status` says whether a conversation happened: `completed` means the caller and an agent were both on the call and it is over (it is billed even if the runtime ended it), `failed` means no conversation took place (nobody connected, or the caller connected and no agent ever joined), `active` means it is in progress, `pending` means the session was created and no one has connected yet, and `unknown` means the platform temporarily lost track of a live call. On a `failed` session where the caller did connect, `started_at`, `ended_at` and `duration_seconds` describe how long they waited; nothing is billed.

`end_reason` says why it ended. It is `null` while a session is live, for a short moment after it ends, and on sessions that predate the field.

| `end_reason`           | `status`    | Meaning                                                                          |
| ---------------------- | ----------- | -------------------------------------------------------------------------------- |
| `user_hangup`          | `completed` | The caller hung up                                                               |
| `agent_hangup`         | `completed` | The agent ended the call (end-call tool, workflow end node, or idle hangup)      |
| `escalated`            | `completed` | The call was transferred to a human. See [Transfer items](#transfer-items)       |
| `conversation_timeout` | `completed` | The call reached its maximum duration                                            |
| `heartbeat_timeout`    | `completed` | The agent runtime stopped responding mid-call                                    |
| `agent_join_timeout`   | `failed`    | The caller connected but no agent joined the call                                |
| `internal_error`       | `completed` | The agent runtime hit an internal error (`failed` when it failed before the conversation started) |
| `llm_endpoint_failure` | `completed` | A [custom LLM](/agents/build/custom-llm) failed repeatedly and the agent hung up |
| `room_join_timeout`    | `failed`    | The caller never connected before the join deadline                              |
| `cancelled`            | `failed`    | The session was ended before anyone connected                                    |
| `dial_failed`          | `failed`    | An outbound call was not answered; `dial_status` has the detail                  |

The same values appear on the [`call.ended` webhook](/agents/monitor/webhooks) and in the dashboard, so the three surfaces never disagree about a session.

### Conversation status

`conversation_status` is one label for how the conversation went. It is derived from `status` and `end_reason`, it is on every row of the list and on the session detail, and you can [filter the list](#filters) by it. The five values below are the current ones; more may be added later, so treat a value you do not recognise as a status you have no special handling for, not as an error. The filter accepts only these five.

| `conversation_status` | Meaning                                                                              | `end_reason`                                                                        |
| --------------------- | ------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------- |
| `active`              | The session is not over yet: `status` is `pending`, `active` or `unknown`             | `null`                                                                              |
| `resolved`            | The conversation ended normally. It does not mean the caller's problem was solved   | `user_hangup`, `agent_hangup`, `conversation_timeout`, or none on a completed session |
| `escalated`           | The call was transferred to a person                                                 | `escalated`                                                                         |
| `missed`              | Nobody connected, so no conversation took place                                      | `room_join_timeout`, `cancelled`, `dial_failed`, or none or any non-error reason on a failed session |
| `error`               | The platform ended the conversation because something failed, or no agent ever joined | `heartbeat_timeout`, `agent_join_timeout`, `internal_error`, `llm_endpoint_failure` |

### Filters

| Parameter                          | Behavior                                                                                              |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `agent_id`                         | Sessions of a single agent                                                                            |
| `status`                           | One of `pending`, `active`, `completed`, `failed`, `unknown`; comma-separate values to match several |
| `end_reason`                       | One or more of the `end_reason` values above, comma-separated                                        |
| `conversation_status`              | One or more of `active`, `resolved`, `escalated`, `missed`, `error`, comma-separated; see [Conversation status](#conversation-status) |
| `caller_number`                    | Exact match on the caller's E.164 number; a bare number gets `+` prepended automatically              |
| `sip_call_id`                      | Exact match on the SIP `Call-ID` of the call's INVITE, for looking up the session behind a carrier CDR entry              |
| `end_user_id`                      | Exact, case-sensitive match on the `end_user_id` you set when [creating the session](/agents/deploy/authenticated-sessions), for listing one customer's sessions |
| `call_sid`                         | Exact match on `call_sid`, for looking up the session behind an [inbound call webhook](/agents/monitor/webhooks#inbound-call-webhook) request |
| `created_after` / `created_before` | ISO 8601 timestamps                                                                                   |

Values inside one comma-separated filter combine with "or": `conversation_status=missed,error` returns the sessions that are either one. Different filters combine with "and": a session has to match every filter you pass, so `status=failed&conversation_status=error` returns only failed sessions whose conversation status is `error`. An unknown value in `conversation_status` returns `400`.

```bash API (curl)
curl "https://api.fish.audio/v1/agent/sessions?conversation_status=missed,error&page_size=50" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

<Note>
  Without a `status` filter the list includes every status, `pending` sessions
  (created, nobody connected yet) among them. Pass `status` to narrow it down.
  Preview calls made from the Builder never appear in this API.
</Note>

### Pagination

Two modes, mutually exclusive (combining them returns `400`):

| Mode   | How                                                                                     | Use it for                  |
| ------ | --------------------------------------------------------------------------------------- | --------------------------- |
| Cursor | Pass the previous response's `next_cursor` as `cursor`; stop when `has_more` is `false` | Crawling, exports, syncing  |
| Page   | Pass `page` (1-based); the response always includes `total`                             | Paged UIs with jump-to-page |

`page_size` defaults to 30, maximum 100; values out of range are rejected. In cursor mode `total` is `null` unless you pass `include_total=true`. Page mode is capped at an offset of 100,000 rows (requests beyond it return `400`), and every page response still includes `next_cursor`, so you can switch to cursor crawling from any page for deep scans.

## Get a session

`GET /v1/agent/sessions/{session_id}` returns the session facts plus a single `items` timeline: messages and tool activity merged in the order they actually happened. It also carries what the platform measured: [startup and per-turn latency](#latency-and-knowledge-retrievals) and the [knowledge lookups](#latency-and-knowledge-retrievals) the agent made.

```bash API (curl)
curl "https://api.fish.audio/v1/agent/sessions/SESSION_ID" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

### Item types

| `type`        | What it is                                                                                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `message`     | One utterance. `role` is `user` or `assistant` (system prompt content is never exposed). `turn_id` groups items belonging to the same conversational turn. `fallback_reason` is `"llm_error"` on a fixed line the agent spoke because its LLM failed, and `null` otherwise. `answered_by_model` names the model that wrote an `assistant` message, the agent's own or an [LLM fallback](/agents/build/llm-fallback). It is `null` on `user` items and on sessions from before the field existed. `interrupted`, `interrupted_by`, `audio_start_ms` and `audio_end_ms` tell you whether a reply was cut off and where the message sits in the recording: see [Interrupted replies and audio position](#interrupted-replies-and-audio-position). |
| `tool_call`   | A tool invocation as it started. `input` is a JSON string, stored in full with no truncation.                                                              |
| `tool_result` | The paired outcome, matched by `call_id`. `status` is `completed` or `failed`. `latency_ms` is the execution time.                                         |
| `transfer`    | One [call transfer](/agents/telephony/transfers) attempt, successful or not. See [Transfer items](#transfer-items).                                        |

Details worth knowing:

- **Role vocabulary**: the history API's `assistant` is the same speaker the [SDK's live events](/agents/deploy/web-sdk) call `agent`.
- **Order**: items are sorted by `created_at` ascending; a `tool_result`'s timestamp is its completion time, so long-running tools appear where they actually finished, with messages in between. Items sharing a timestamp order `message`, then `tool_call`, then `tool_result`.
- **`tool_source`**: where the tool ran, one of `client`, `webhook`, `builtin` (platform tools such as call transfer and hang-up), `mcp` (tools from a connected MCP server), `background` (work the agent delegated to a background task), or `unknown` (calls recorded before source attribution). Treat it as an open set. See [Tools](/agents/build/tools).
- **Payloads**: `input` and `output` are JSON strings, symmetric with the live SDK events, so one parser covers both. `output` and `error` are stored up to 256 KB; beyond that the text is cut and `output_truncated` is `true`.
- **Mid-call queries**: you can fetch an `active` session; you get the items persisted so far, and `analysis` is `null` until [post-call analysis](/agents/monitor/post-call-analysis) completes.
- A `tool_call` without a matching `tool_result` means the execution never resolved.
- **`rejected_by`**: on a `tool_result`, `"parameter_validation"` when the tool [validates its parameters](/agents/build/webhook-tools#parameters-and-validation) and refused the call before it ran, so `status` is `failed` and `error` is the rejection the model was shown. `null` for every other result, including a tool that ran and failed. New values may be added.
- **`error_detail`**: on a failed `tool_result`, the structured reason beside the `error` text: `status_code`, a stable code to count and match on; `sip_status`, the carrier's SIP response code, or `null`; and `status_message`, a readable explanation. Only `_transfer_call` sets it so far; see [reason codes on the tool result](/agents/telephony/transfers#reason-codes-on-the-tool-result) for its codes. `null` on completed results, on tools that only set `error`, and on results recorded before the field existed.

### Interrupted replies and audio position

An `assistant` message that was cut off before it finished has `interrupted: true`, and its `content` is roughly the part that was spoken: it can run a few words past the point where playback stopped. `interrupted_by` says what cut it off:

| `interrupted_by` | What cut the reply off                                                   |
| ---------------- | ------------------------------------------------------------------------ |
| `user_speech`    | The caller talked over it                                                |
| `user_message`   | The user sent a typed message                                            |
| `keypad`         | A key press                                                              |
| `client`         | Your client sent an interrupt                                            |
| `session_end`    | The session ended in the middle of the reply, for example the caller hung up |

New values may be added, so treat a value you don't know as an unspecified cause. `interrupted` is `null` on complete replies, on `user` messages, and on sessions recorded before the field existed. It is never `false`. `interrupted_by` is `null` whenever `interrupted` is, and on older cut-off replies that did not record a cause.

`audio_start_ms` and `audio_end_ms` locate a message in the [recording](#download-recordings), in milliseconds from the start of the speaker's own track: the `agent` track for `assistant` messages, the `user` track for `user` messages. Each speaker has a separate track, so the numbers are not relative to the session start or to one mixed file. To play a reply, take the `agent` track's URL from the recording response and seek to `audio_start_ms`. The positions are approximate: the start is reliable, but the end of a reply that played to the finish can be a few seconds late, and a `user` message can be offset, or `null` when one turn holds several user messages. Both fields are `null` when the session has no recording, when the position cannot be told, and for `assistant` messages when the agent has more than one `agent` track (an agent with a [background sound](/agents/build/background-sound-voice-effect#recordings)).

### Latency and knowledge retrievals

`startup_ms`, `turns` and `unattributed_knowledge_retrievals` are on the session detail. `turns` and `unattributed_knowledge_retrievals` are empty lists on a session that never recorded them.

- **`startup_ms`**: how long the session took to start, in whole milliseconds, from the request that created it until the agent was ready to talk. It is `null` when either end was not recorded, for example while the session is still starting.
- **`turns`**: one entry per conversation turn, ascending by `turn_id`. The `turn_id` is the one on the `items` of that turn, so you can put a turn's messages and its measurements together.
- **`unattributed_knowledge_retrievals`**: knowledge lookups that belong to no turn.

Each entry of `turns` has:

| Field                  | What it is                                                                                                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `turn_id`              | The turn number, as on `items`                                                                                                   |
| `latency_summary`      | The turn's first-response latency, in whole milliseconds. Each value is `null` when it could not be measured                    |
| `timings`              | The turn's timing steps in milliseconds. When a step was reported more than once, the latest value is shown                      |
| `knowledge_retrievals` | The knowledge lookups the agent made in this turn                                                                                |

`latency_summary` is a short, stable summary of the turn. Use it for dashboards and alerts. It has these fields:

| Field                     | What it measures                                                                                                           |
| ------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `eou_ms`                  | The delay of the end-of-utterance decision                                                                                 |
| `llm_ms`                  | LLM time to first token                                                                                                    |
| `tts_ms`                  | Speech synthesis time to first audio byte                                                                                  |
| `voice_to_voice_ms`       | From the caller finishing speaking to the first agent audio                                                                |
| `voice_to_voice_heard_ms` | The same interval as the caller's browser heard it. Only web sessions whose client reported playback timing have it         |

`timings` has a fixed set of keys, all durations in whole milliseconds. A step the turn has no measurement for is `null`. Steps that do not apply to a session (the `client_*` ones exist only for web sessions) are `null` too.

| Key                                       | What it measures                                                                         |
| ----------------------------------------- | ---------------------------------------------------------------------------------------- |
| `eou_delay_ms`                            | Delay of the end-of-utterance decision after the caller stopped speaking                 |
| `llm_ttft_ms`                             | Time from the LLM request to its first token                                             |
| `tts_ttfb_ms`                             | Time from the speech request to the first audio byte                                     |
| `speaking_after_speech_stop_ms`           | From the caller finishing speaking to the agent's first audio (voice to voice)           |
| `speech_duration_ms`                      | How long the caller spoke in this turn                                                   |
| `transcription_delay_ms`                  | Delay before the caller's speech was transcribed                                         |
| `on_user_turn_completed_delay_ms`         | Time spent in the step that runs before the LLM request                                  |
| `thinking_after_transcript_ms`            | Time from the finished transcript until the agent started to think                       |
| `thinking_to_speaking_ms`                 | Time from the agent starting to think until it started to speak                          |
| `llm_duration_ms`                         | How long the LLM took to finish its reply                                                |
| `tts_first_byte_after_eou_ms`             | Time from the end-of-utterance decision to the first audio byte                          |
| `tts_duration_ms`                         | How long speech synthesis took                                                           |
| `tts_audio_duration_ms`                   | Length of the audio that was synthesized                                                 |
| `assistant_complete_after_speech_stop_ms` | From the caller finishing speaking to the agent's reply being complete                   |
| `voice_to_voice_heard_ms`                 | Voice to voice as the caller's browser heard it. Only web sessions whose client reported playback timing have it |
| `client_delay_estimate_ms`                | The caller's own estimate of playback delay, from WebRTC statistics                      |
| `client_rtt_ms`                           | Round trip time between the caller and the platform's edge                               |
| `client_jitter_buffer_ms`                 | The caller's jitter buffer                                                               |

New steps may be added as new keys over time, so read `timings` by key and ignore the keys you do not know.

A knowledge lookup in `knowledge_retrievals` or `unattributed_knowledge_retrievals` has the `query` the agent searched for, the `hits` it got back, and an `error` that is set when the lookup failed (the `hits` are then empty and the turn ran without the knowledge). A hit carries `knowledge_source_id`, `revision_id`, `chunk_id`, `chunk_index`, `score`, `source_name` and `file_name`. `knowledge_source_id` is the id of the source in the [knowledge APIs](/api-reference/endpoint/agent/list-knowledge-sources). To read the text of a hit, see [Read a knowledge chunk](#read-a-knowledge-chunk).

```json
{
  "query": "return policy",
  "hits": [
    {
      "knowledge_source_id": "ks_8f2…",
      "revision_id": "rev_41c…",
      "chunk_id": "chunk_77d…",
      "chunk_index": 3,
      "score": 0.83,
      "source_name": "Help center",
      "file_name": "returns-policy.md"
    }
  ],
  "error": null
}
```

### Read a knowledge chunk

A hit names a chunk but not its text. `GET /v1/agent/sessions/{session_id}/knowledge-chunks/{chunk_id}` returns the text, so you can see what the agent was given. Take `chunk_id` from a hit, and pass the hit's `knowledge_source_id` and `revision_id` as the two required query parameters.

```bash API (curl)
curl "https://api.fish.audio/v1/agent/sessions/SESSION_ID/knowledge-chunks/CHUNK_ID?knowledge_source_id=KNOWLEDGE_SOURCE_ID&revision_id=REVISION_ID" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

```json
{
  "knowledge_source_id": "ks_8f2…",
  "revision_id": "rev_41c…",
  "chunk_id": "chunk_77d…",
  "chunk_index": 3,
  "file_name": "returns-policy.md",
  "content": "Returns. You can return any item within 30 days of delivery for a full refund. …",
  "truncated": false
}
```

`content` is cut at 4000 characters, and `truncated` is `true` when the chunk is longer. Both query parameters are required. The endpoint only reads chunks that this session's own retrievals returned: any other combination of ids answers `404`, and so does a chunk that has since been removed from the knowledge base. It returns `410` when the session's content was already deleted by data retention. See the [endpoint reference](/api-reference/endpoint/agent/get-agent-session-knowledge-chunk).

### LLM endpoint errors

Sessions on a [custom LLM](/agents/build/custom-llm) also carry `llm_endpoint_errors`. It lists each failed generation of your endpoint, oldest first. It is empty when the agent runs on a platform model or your endpoint never failed.

```json
{
  "end_reason": "llm_endpoint_failure",
  "llm_endpoint_errors": [
    {
      "occurred_at": "2026-10-15T15:45:10Z",
      "turn_id": 3,
      "type": "http_error",
      "reason": null,
      "status_code": 502,
      "response_body": "{\"detail\":\"no tunnel\"}",
      "duration_ms": 812,
      "consecutive_failures": 1
    }
  ]
}
```

- `turn_id` is the turn the failed reply belonged to. It uses the same numbering as `message` items.
- `type` is `http_error`, `timeout`, `connection_error` or `invalid_response`. See [Failure behavior](/agents/build/custom-llm#failure-behavior). New types may be added.
- `reason` is set on `connection_error` and `invalid_response` only. New reasons may be added.
  - `connection_error`: `dns_failed`, `connection_refused`, `connection_reset`, `tls_failed`, `address_not_allowed` (an address the platform does not call) or `unknown`.
  - `invalid_response`: `not_event_stream` (a streamed request got something else back), `stream_incomplete` (the stream ended with no `finish_reason`, usage or output), `empty_reply` (no text and no tool call) or `unknown`.
- `status_code` is set on `http_error` only.
- `response_body` is the start of what your endpoint sent back, on `http_error` and `not_event_stream` only. It is at most 300 characters, and your API key is masked. It is `null` when the body was empty.
- `duration_ms` is the time from the request to the response or the failure. It is `null` when it was not measured.
- `consecutive_failures` counts failures in a row. The agent hangs up at the third.

### LLM fallbacks

`llm_fallbacks` lists every reply that moved to another model, oldest first. See [LLM Fallback](/agents/build/llm-fallback). It is empty when the agent's own model answered every reply.

```json
{
  "llm_fallbacks": [
    {
      "occurred_at": "2026-10-15T15:45:10Z",
      "turn_id": 3,
      "from": { "model": "openai/gpt-6.1-terra-fast" },
      "to": { "custom": { "base_url": "https://llm.example.com/v1", "model": "backup-70b" } },
      "reason": "ttft_timeout"
    }
  ]
}
```

- `turn_id` is the turn the reply belonged to, the same numbering as `message` items.
- `from` and `to` each name a model. A platform model is `{ "model": "<platform model id>" }`. A custom endpoint is `{ "custom": { "base_url": "…", "model": "…" } }`. The endpoint's key is never included.
- `reason` is one of:

  | `reason` | Meaning |
  |---|---|
  | `error` | The model's provider returned an error. |
  | `timeout` | No reply within the platform's own time limit (outside `manual` mode). |
  | `ttft_timeout` | The model did not [start its reply](/agents/build/llm-fallback#when-a-reply-has-started) within its `ttft_timeout_ms`. |
  | `total_timeout` | The model's `total_timeout_ms` ran out before it started its reply. |
  | `empty` | The response stream broke off with no output and no end signal. A reply that finished normally with nothing in it is the agent staying silent. That is not a fallback. |
  | `kick_in` | The fallback ran in parallel and its reply was used. The agent's own model had not started its reply within `kick_in_ms`. |

  New reasons may be added.

<Warning>
  `items` is a discriminated union on `type`, and it evolves additively. Ignore
  item types and fields you don't recognize. New modalities and item kinds will
  appear without a version bump.
</Warning>

### Transfer items

When the agent [transfers a phone call](/agents/telephony/transfers), each attempt becomes one `transfer` item, including attempts that failed. Its `call_id` is the `call_id` of the `_transfer_call` `tool_call` that started it, and its `created_at` is when the attempt started, which is where it sits in the timeline. Every field is always present and is `null` when there is no value.

```json
{
  "type": "transfer",
  "call_id": "tool_3c1…",
  "destination": "Front desk",
  "destination_type": "phone",
  "target": "+14155550123",
  "mode": "warm",
  "warm_connect": "confirm",
  "outcome": "merged",
  "sip_status": null,
  "dial_status": null,
  "decline_reason": null,
  "consult_end_reason": null,
  "hold_started_at": "2026-07-22T09:15:40Z",
  "hold_ended_at": "2026-07-22T09:16:25Z",
  "dial_started_at": "2026-07-22T09:15:41Z",
  "answered_at": "2026-07-22T09:15:57Z",
  "ended_at": "2026-07-22T09:16:25Z",
  "transferred_call_ended_at": "2026-07-22T09:30:11Z",
  "transferred_call_duration_seconds": 826,
  "transferred_call_end_reason": "caller_hangup",
  "messages": [
    {
      "role": "assistant",
      "content": "Hi, I have a caller who needs help with a delivery. Can you take the call?",
      "created_at": "2026-07-22T09:15:59Z"
    },
    {
      "role": "transfer_target",
      "content": "Sure, put them through.",
      "created_at": "2026-07-22T09:16:21Z"
    }
  ],
  "created_at": "2026-07-22T09:15:39Z"
}
```

| Field                               | Description                                                                                                                                                                                               |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `call_id`                           | The `call_id` of the `_transfer_call` tool call that started the attempt.                                                                                                                                 |
| `destination`                       | The destination's name at the time of the call. An empty string when the agent has a single unnamed destination.                                                                                          |
| `destination_type`                  | `phone` or `sip`.                                                                                                                                                                                         |
| `target`                            | The E.164 number or SIP URI that was dialed.                                                                                                                                                              |
| `mode`                              | `cold` or `warm`.                                                                                                                                                                                         |
| `warm_connect`                      | `confirm`, `briefing`, or `direct` on warm transfers. `null` on cold transfers.                                                                                                                           |
| `outcome`                           | How the attempt ended. `merged` and `referred` are the successful ones. See [Transfer results](/agents/telephony/transfers#transfer-results) for every value. `null` while the attempt is in progress.    |
| `sip_status`                        | `dial_failed` and `refer_failed` only: the final SIP response code the carrier returned, such as `486`. `null` when the carrier gave none.                                                                |
| `dial_status`                       | `dial_failed` and `refer_failed` only: `busy`, `no_answer`, or `failed`. See [Why a call did not connect](/agents/telephony/transfers#why-a-call-did-not-connect) for how each is decided.                |
| `decline_reason`                    | `declined` only: the agent's short summary of why your team member declined. `null` when they gave no reason. What they actually said is in `messages`.                                                   |
| `consult_end_reason`                | `consult_closed` only: how the consult call ended before the calls were merged, `transfer_target_hangup` or `connection_lost`. `null` when the platform could not tell.                                   |
| `hold_started_at`                   | Warm: when the caller started hearing hold music.                                                                                                                                                         |
| `hold_ended_at`                     | Warm: when the caller came off hold, connected to your team member or back with the agent.                                                                                                                |
| `dial_started_at`                   | Warm: when the platform started dialing the destination.                                                                                                                                                  |
| `answered_at`                       | Warm: when the destination answered the consult call.                                                                                                                                                     |
| `ended_at`                          | When the attempt reached its outcome: the merge on a warm transfer, the completed handoff on a cold one (normally the moment the destination answered), or the failure.                                   |
| `transferred_call_ended_at`         | `merged` and `referred` only: when the call between the caller and your team member ended. See [After the transfer](#after-the-transfer).                                                                 |
| `transferred_call_duration_seconds` | `merged` and `referred` only: how long that call lasted. Warm: from `ended_at` to `transferred_call_ended_at`. Cold: the duration on the carrier's call record.                                           |
| `transferred_call_end_reason`       | `merged` only: how that call ended. Always `null` on cold transfers.                                                                                                                                      |
| `messages`                          | Warm: the transcript of the private consult call. `role` is `assistant` (the agent briefing) or `transfer_target` (the person it dialed). These lines never appear among the caller's `message` items.    |

A warm transfer's consult call is also recorded when the session [records audio](#what-gets-stored). Its tracks are under `transfers` in the [recording response](#download-recordings), where `transfer_id` is the item's `call_id`.

#### After the transfer

On a successful transfer the session ends with `end_reason` `escalated`, whatever happens on the call afterwards. The three `transferred_call_*` fields describe that call between the caller and your team member.

`transferred_call_end_reason` is one of:

| Value                    | Meaning                                                                                                                                                                          |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `caller_hangup`          | The caller hung up. On an [outbound call](/agents/telephony/outbound-calls), this is the person the agent called.                                                                |
| `transfer_target_hangup` | Your team member hung up.                                                                                                                                                        |
| `conversation_timeout`   | The call reached the agent's [maximum call duration](/agents/build/configuration#call-duration). The limit counts from the start of the call, time before the transfer included. |
| `connection_lost`        | One of the lines dropped. Nobody hung up.                                                                                                                                        |
| `null`                   | The platform could not tell how the call ended.                                                                                                                                  |

When the values arrive depends on the mode:

- **Warm**: when the call ends. They are `null` while the caller and your team member are still talking.
- **Cold**: the platform leaves the call at the handoff, so the end time and duration come from the carrier's call record. They appear up to about an hour after the call ends. Who hung up is never known, so `transferred_call_end_reason` stays `null`.
- **Cold transfers on [imported SIP numbers](/agents/telephony/byo-sip)**: the call record stays with your carrier, so the three fields stay `null`.

When `transferred_call_ended_at` is `null`, the other two are `null` as well. A `referred` item with a duration of `0` means the carrier's record shows the destination never picked up, for example because the caller hung up while it was still ringing.

### Correlate with live events

`call_id` is the same identifier your client receives in the SDK's `toolCallStarted` / `toolCallCompleted` / `toolCallFailed` events. Log it live, and you can align in-call UI with the post-call record: jump from a tool chip in your interface straight to the matching `tool_call` / `tool_result` pair in history. See the [Web SDK](/agents/deploy/web-sdk).

## Download recordings

`GET /v1/agent/sessions/{session_id}/recording` returns the recording status and signed download URLs: one audio track per speaker, so you can play or process the agent and the user separately. An agent with a [background sound](/agents/build/background-sound-voice-effect#recordings) has a second `agent` track, which holds the ambience. For sessions that never [recorded](#what-gets-stored) (recording turned off, or no audio produced), the endpoint returns `404`.

```bash API (curl)
curl "https://api.fish.audio/v1/agent/sessions/SESSION_ID/recording" \
  --header "Authorization: Bearer $FISH_API_KEY"
```

Signed URLs are short-lived: store the `session_id` and request fresh URLs when you need the audio. For the same reason, recordings are not embedded in the session detail response.

Neither the list nor the session detail says whether a session has a recording. Ask the recording endpoint: it answers with the status and URLs of each track, and `404` when the session has none.

## Access semantics

- Your API key sees every production session across your team's workspaces, from all sources.
- A session that doesn't exist, or belongs to another team, always returns `404`, never `403`. The [recording endpoint](#download-recordings) additionally returns `404` for a session that exists but was never recorded.
